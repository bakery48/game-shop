# 中古ゲームショップ経営＋架空ソフト収集 — プロトタイプ

仕様書 v0.1 の「10. プロトタイプの範囲」に対応した検証用の実装です。
目的は**資金カーブと図鑑の埋まり方が想定通りかを検証すること**で、面白さの確認は対象外です。
仕様書の方針どおり、これは捨てる前提のコードです。

## 動かす

**ブラウザ版**（見た目は表とボタンのみ）

    index.html をブラウザで開くだけ（ビルド不要・サーバ不要）

配布用に1ファイルへまとめたものが `dist/prototype.html` です。
このファイル単体をブラウザにドラッグするだけで動きます。作り直すには:

    node build/build.js

- 「1ターン自動 / 1週自動 / 最後まで自動」で自動プレイの挙動を確認できます
- 「シミュレーション100回」はブラウザ内で 100 周まわして分布を出します
- seed を変えると同じ条件を再現できます（ソフト150本の内容は seed によらず固定）

**自動シミュレーション**（Node.js）

    node src/sim.js            # 100回
    node src/sim.js 300        # 回数指定
    node src/sim.js 100 --runs=3   # 図鑑を引き継いで3周まわし、周ごとの成績を出す
    node src/sim.js 100 --json # 機械可読
    node src/sim.js 100 --balance=rent=20000,startCash=200000   # 定数を上書きして比較

## ファイル

| ファイル | 中身 |
|---|---|
| `data/software.json` | **架空ソフトのマスターデータ（手書き60本）**。ここを編集すれば内容が変わる |
| `src/catalog.js` | 150本のカタログ生成。手書き60本＋自動生成90本を合成する |
| `src/software-data.js` | `data/software.json` から自動生成（`node build/gen-data.js`）。ブラウザ用 |
| `src/engine.js` | ゲーム本体。**バランス定数は先頭の `BALANCE` に集約** |
| `src/policy.js` | 自動プレイの方針。資金カーブ検証の基準線 |
| `src/sim.js` | 100回まわして分布と検証項目を出す |
| `src/ui.js` / `index.html` | ブラウザ版UI |
| `build/build.js` / `build/template.html` | `dist/prototype.html`（単一ファイル版）を作る |
| `build/gen-data.js` | `data/software.json` → `src/software-data.js` |

`src/engine.js` と `src/policy.js` はブラウザと Node の両方から使えます。

## 検証結果（300回シミュレーション）

| 週 | 残高（中央値） | 10%〜90% | 登録 | 所持 |
|---:|---:|---|---:|---:|
| 5 | 100,460円 | 59,890 〜 158,710 | 70 | 31 |
| 10 | 226,010円 | 99,390 〜 387,420 | 91 | 36 |
| 25 | 148,630円 | 5,130 〜 356,946 | 125 | 90 |
| 40 | 461,175円 | 8,850 〜 1,201,080 | 141 | 128 |
| 50 | 1,107,774円 | 11,050 〜 2,064,087 | 144 | 142 |

| 検証項目 | 結果 |
|---|---|
| 10週目の残高は10万円前後か | **×** 226,010円（5週目が100,460円。後述9） |
| 25週目に図鑑80本に届くか | **○** 125本（むしろ速い） |
| 50週で150本所持は達成可能か | **○** 最高150本・真エンド4回／300回 |
| 家賃が圧力として機能しているか | **○** 残高が家賃を割る週が平均7.5回、閉店率9% |

最終所持数の分布（300回）:

| 所持数 | 回数 |
|---|---:|
| 150本（真エンド） | 4回（1%） |
| 145〜149本 | 80回（27%） |
| 140〜144本 | 74回（25%） |
| 100〜139本 | 26回（9%） |
| 99本以下 | 116回（39%） |

**「あと数本で届かない」が過半、完全クリアが1%** で、仕様書のいう「可能だが余裕はない」に収まりました。
99本以下の39%は、据え置きを決めた強制売却スパイラルに落ちた回です（後述5）。

## 仕様書の数値について見つかった問題

プロトタイプの主目的はここです。**仕様書 v0.1 の数値のままでは成立しません。**
以下は実装して測った結果わかったことと、暫定的に採った対処です。

### 1. 店番の売上が家賃に対して1桁足りない（最重要）

仕様書の「客3〜4人／ターン」で実装すると、1ターンに売れるのは**最大でも2本前後**です。
50週＝100ターンで170本、平均単価2,518円で**通算42万円**にしかなりません。
家賃だけで50週に150万円かかるので、どう調整しても破産します（初期実装では100%が3週目で閉店）。

仕入れ値・卸値・客数・家賃を総当たりで振っても改善しませんでした。構造的な上限だからです。

**対処**: 客を「判断が要る客（3〜4人）」と「店頭で普通に売れる分」に分けました
（`BALANCE.passiveSales`、既定 7〜12本／ターン）。陳列棚＝売り物という意味づけは変えていないので、
ときメモ風の固定画面・低クリック数を保ったまま売上を成立させられます。

**判断が必要**: 来店数を増やすのか、この分離を採るのか、家賃を下げるのか。

### 2. 開始資金50,000円では2週で詰む

開始資金50,000円＋初期在庫30本（卸価値 約14,000円）に対して家賃は週30,000円で、
運転資金は実質2週分しかありません。まとめ買い1回（30,000〜80,000円）すら打てません。

**対処**: 開始資金を **100,000円** に変更しました。これで閉店率が5%に落ち着きます。

### 3. 棚50枠では150本を同時所持できない（真エンドが定義上不可能）

完全クリア条件は「150本すべてを同時に所持」ですが、初期棚枠は50です。
5節にある棚拡張（最大200枠・10万円）は10節では「作らないもの」に入っていますが、
**これが無いと真エンドに到達できません**。行動フェイズの選択肢として実装しました。

### 4. 激レア15本は「購入」させると破綻する

激レア15本の相場合計は **252万円**（全150本で360万円）です。
オークションで買える設定にすると、資金がすべて吸われて閉店率が45%に跳ね上がります。
8節どおり**イベント報酬**にすれば経済はほぼ閉じます。

**対処**: `BALANCE.ultra.source` で `'event'` / `'auction'` / `'both'` を切り替えられます（既定 `'both'`）。
常連イベントは未実装なので、`'event'` は「12週目以降2週ごとに未所持の激レアが1本手に入る」で代用しています。

なお、4節の「激レアが高額なのは終盤の資金の受け皿にするため」と
8節の「イベント報酬で手に入る」は両立しません。どちらを採るか決める必要があります。

### 5. 強制売却が回復不能な死のスパイラルになる

6節の「家賃が払えない場合は在庫を強制売却」は、一度発動すると
**在庫が減る→売上が落ちる→また払えない**の悪循環に入り、まず戻れません。
測定では、強制売却が0回だったゲームは所持115〜141本、1回でも起きたゲームは所持44本以下という
極端な二極化が出ました。救済措置（分割払い、前借り、猶予週）を検討すべきです。

### 6. 図鑑の埋まりが想定より速い

25週で登録119本（仕様書の想定は80本）。まとめ買い1回で30〜50本入るので登録は一気に進みます。
一方で**所持**は50週かけて120本前後にしか届きません。
仕様書が意図した「登録率90% / 所持率60%」という二層表示は、実測では
**登録93% / 所持80%** に近い形になりました。二層構造そのものは有効に機能しています。

### 7. 「最後の1本を売るか」がゲームの中心にある

自動売上を無条件に許すとコレクションが流出し（1ゲームあたり356回、最後の1本が売れていました）、
逆に全部を守ると売り物が尽きて破産します。
そこで在庫ごとに**「非売品」札**を付けられるようにしました。所持率が下がる売却は必ず判断を通ります。
仕様書に無い要素ですが、無いとゲームが成立しませんでした。

## 世界設定とソフトのデータ

ハードは **SEC（スーパーエレクトリックコンピュータ、通称スーエレ）** の1機種。
カセット式の据置機で、マルチタップ、カセット内蔵の特殊チップ、コンビニでの書き換えサービスに対応していた、
という設定です。

ソフトのマスターデータは `data/software.json` にあります。手書きが60本、残り90本は自動生成の仮データです
（UI上では `*` が付き、詳細に「仮データ」と表示されます）。JSONに追記すれば、その分だけ自動生成が減ります。

    node build/gen-data.js   # JSONを編集したら実行（ブラウザ用のJSを作り直す）

`title` / `maker` / `genre` / `rating` / `details` が手書きの原文で、
`tier`（希少度）/ `base`（基準相場）/ `year`（発売年）はプロトタイプ用にこちらで起こした値です。
`details` の記述から起こしているので、書き換えても構いません。

| detailsの記述 | 起こした値 |
|---|---|
| 「中古市場で10万円以上のプレミア」 | 激レア・120,000円 |
| 「限定100本配布」「数百万円で取引」 | 激レア・260,000円 |
| 「発売2週間でワゴンに980円で山積み」 | 並品・500円 |
| 「買い取り価格が発売初週で10円」 | 並品・500円 |
| 「発売日に学校を休む子供が続出」＝大ヒット | 並品・900円（誰もが持っているので安い） |

大ヒット作が安く、回収騒ぎや書き換え専用が高いのは中古市場の実態に合わせたものです。

## 決定済みの設計判断

プロトタイプの結果を受けて確定した項目です。

| 論点 | 決定 |
|---|---|
| 店の売上の作り方 | **自動売上を分離**（判断が要る客3〜4人＋店頭で普通に売れる分7〜12本） |
| 激レア15本の入手経路 | **イベント報酬とオークション購入の両方**（`ultra.source: 'both'`） |
| 家賃未払いの処理 | **強制売却のまま**（§6どおり。救済措置は設けない） |
| 150本コンプの扱い | **到達可能まで経済を強化**（真エンド率1%で着地） |
| 序盤の緊張感 | **選択肢を絞る**（単品入札・棚拡張・取り寄せは11週目から解禁。序盤はロットの質も客足も低い） |
| 周回引き継ぎ | **図鑑の登録だけ引き継ぐ**（資金・在庫・棚枠は毎周ゼロから）。真エンドは実質「2周目以降の特典」 |

### 8. 「最後の数本を狙い撃つ」手段が存在しなかった

3節は「46〜50週: 最後の数本を狙い撃つ。売らずに買い戻す局面へ」と書いていますが、
仕様書のどこにも**特定のソフトを指名して入手する手段がありません**。
まとめ買いも持ち込みもオークションもすべてランダムなので、
図鑑には載っている（＝一度は手にした）のに二度と戻ってこないソフトが平均20本残り、
所持率は約70%で頭打ちになりました。

**対処**: 「取り寄せ」を追加しました。図鑑に載っているソフトを相場の160%で指名して仕入れられます。
これで所持率の頭打ちが解消し、真エンドが到達可能になりました。
割増料金が終盤の資金の受け皿も兼ねるので、4節の「激レアを資金の受け皿にする」意図も部分的に満たします。

### 9. 序盤の緊張感と150本コンプは同時に満たせない

「1〜10週は家賃を払うのがやっと」を作るため、序盤の選択肢を絞りました。
単品入札・棚拡張・取り寄せを11週目から解禁し、序盤はロットの質も客足も低く抑えています。
結果、**5週目の残高は100,460円**まで下がり、序盤の手触りは仕様書に近づきました。

ただし**10週目は226,010円で、想定の10万円前後には届きません**。
これ以上絞ると、下がるのは残高より先に生存率のほうです。実測すると:

| 序盤の締め付け | 10週目残高 | 崩壊率（所持99本以下） |
|---|---:|---:|
| なし | 333,000円 | 17% |
| 弱 | 283,000円 | 23% |
| 中（採用） | 229,000円 | 33% |
| 強 | 159,000円 | 78% |

10週目の残高を10万円台に落とすには崩壊率が7割を超えます。
原因は5節の強制売却スパイラルで、**「カツカツ」と「詰み」の間に中間状態が無い**ためです。
序盤の緊張感を数値どおりに作りたい場合、避けて通れないのは家賃未払いの救済措置の追加になります。

### 10. 真エンドは1周目には重すぎる — 周回引き継ぎで解く

150本すべての同時所持は、1周目だと真エンド率がほぼ1%です。
これは「チャレンジ要素として、たまにうまくいく」水準としては妥当ですが、
到達手段としては細すぎます。

**対処**: 周回引き継ぎ（12節の未決定事項）を実装しました。引き継ぐのは
**図鑑の登録だけ**です。資金も在庫も棚枠も毎周ゼロから始まるので、経営の難度は変わりません。
ただし登録済みのソフトは最初から取り寄せで指名できるため、完全クリアが現実的な射程に入ります。

| 周 | 開始時の図鑑 | 登録率 | 所持率（中央値） | あと一歩 | 真エンド | 閉店 |
|---:|---:|---:|---:|---:|---:|---:|
| 1周目 | 26本 | 95% | 93%（140本） | 19% | **0〜1%** | 10% |
| 2周目 | 144本 | 99% | 96%（144本） | 44% | **15%** | 7% |
| 3周目 | 149本 | 100% | 95%（143本） | 46% | **23%** | 11% |

3周目でも真エンドは23%までしか上がりません。図鑑が完成していても、
50週目の時点で150本を**同時に**持っているのは別の難しさだからです。
知識が揃っても作業ゲーにはならない、という点でこの引き継ぎ設計は機能しています。

## 総数を増やした場合（参考）

「150本より増やせるか」を測った結果です。本数ごとに最適な立ち回り
（非売品にする時期を本数に応じて遅らせる）をさせています。

| 総数 | まとめ買い回数 | 棚に入れた延べ本数 | 登録実数 | 登録率 | 所持率（中央値） | 真エンド（1周目） |
|---:|---:|---:|---:|---:|---:|---:|
| 100本 | 60回 | 1,120本 | 100 | 100% | 99% | 27% |
| **150本** | 60回 | 1,117本 | 147 | 98% | 95% | 〜1% |
| 200本 | 60回 | 1,082本 | 187 | 94% | 87% | 0% |
| 250本 | 58回 | 1,068本 | 218 | 87% | 63% | 0% |
| 300本 | 54回 | 939本 | 233 | 78% | 5% | 0% |
| 400本 | 33回 | 691本 | 252 | 63% | — | 0% |

総数を増やしても登録実数は伸び続けますが、増え方が総数の1/4以下に落ちます。
原因は3つが重なっています。

**1. 延べ入手数に上限がある（約1,100本）**
行動フェイズは100ターン固定で、まとめ買いに使えるのは最大60回程度。
1ロットで棚に入るのは約18本だけです（残りは枠あふれでその場で業者行き＝図鑑に載らない）。
60回 × 18本 ≈ 1,080本が全体の予算になります。

**2. 同じものを何度も引く（クーポンコレクター）**
1,100回引いても中身は重複だらけです。均等に引けた場合の理論値は
`総数 × (1 − e^(−1100/総数))` で、300本なら287本。

**3. レア帯が構造的に引かれにくい（これが本命）**
実測は理論値より常に低く、しかも差が開きます。ロットの中身の比率が固定だからです。
ロットから出るレアは5.5%固定なのに、カタログではレアが23%（35/150）を占めます。
総数を増やすとレアの本数だけが比例して増えるため、レア1本あたりの遭遇率が反比例して下がります。

| 総数 | 並品 | 中堅 | レア | 激レア |
|---:|---:|---:|---:|---:|
| 150本 | 97% | 100% | 94% | 100% |
| 200本 | 92% | 95% | 78% | 90% |
| 250本 | 85% | 88% | 60% | 68% |
| 300本 | 77% | 77% | **49%** | 53% |

レアが先に破綻します。300本だと半分のレアは存在すら知らないまま50週が終わります。

**副作用: 延べ入手数自体も減る**
総数が増えると在庫の大半が「コレクション＝非売品」になり、売り物の重複が減って収入が落ち、
ロットを買う資金が回らなくなります（400本でまとめ買いが60回→33回に減少）。
本数を増やすと経営そのものが痩せる、という二次効果です。

総数を増やしたい場合は、ロットのレア含有率（`BALANCE.bulk.mix.rare`）を
総数に連動させれば緩和できます（150本で5.5%なら300本では11%）。
